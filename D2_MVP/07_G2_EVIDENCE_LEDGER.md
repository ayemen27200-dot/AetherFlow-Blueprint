## 1. كيفية وصول ملف الرفع إلى العامل (تزويد العامل بالملف)

عقد الفصل ثابت ومُختبَر، ولا توجد نقطة تنزيل عامة:

```
عميل الـAPI                الطابور (SQLite)                العامل (الحاويتان تتشاركان /app/data)
     │                          │                                     │
     │  POST /jobs {file: "<id>"}                                       │
     │  (id opaque فقط، بلا مسارات)  validate_upload_id                 │
     │ ────────────────────────► │  يخزَّن: upload://<id>               │
     │                            │ ──────────────────────────────────► │ LocalUploadStore.resolve(id)
     │                            │                                     │  - إعادة تحقق من رمز الـid
     │                            │                                     │  - ربط داخل AETHERFLOW_UPLOAD_STORE
     │                            │                                     │  - حل الروابط الرمزية وفحص الاحتواء
     │                            │                                     │  - ملف عادي موجود داخل الجذر الموثوق
     │                            │                                     │  ▼
     │                            │                                     │ منفّذ FFmpeg ثم مخرجات نسبية
```

- الـAPI لا يقبل مسارات خادم إطلاقًا؛ `POST /uploads` **خارج نطاق D2** (D3).
- التزويد الفعلي للكائن داخل `AETHERFLOW_UPLOAD_STORE` يتم بقناة تشغيلية خارج
  الـAPI (إيداع مُوثَّق من مُشغّل/مكوّن استيعاب لاحق باسم الرمز المتحقَّق منه)؛
  في Compose الجذر داخل المجلد المتشارك `/app/data/upload_store` فتصل إليه
  حاويتا orchestrator وworker عبر نفس وحدة التخزين.
- فشل الحل يُغلق بمهمة `failed/INVALID_INPUT` بلا مسارات في الرسالة.

| Caddy/Let's Encrypt | مُثبَت جزئيًا | سجلات الرانر في التشغيلات السابقة أظهرت إصدار شهادة داخلية `tls internal` لـlocalhost بنجاح (`issuer: local`) والخدمة مستمعة على 80/443؛ شهادة Let's Encrypt عامة تبقى غير مُثبَتة وتحتاج مضيفًا بـDNS حقيقي ومنافذ عامة |

### ماذا يغطي `scripts/verify_compose_stack.sh` (10 أقسام)

`docker compose config` ← عينة سليمة وتالفة في مجلد بيانات معزول ← بناء
وتشغيل المكدس ← فحوص health عبر شبكة Compose الداخلية ← queued→completed عبر
HTTP حقيقي بنداءات curl من داخل حاوية orchestrator (لا من المضيف) ← فك ترميز
مستقل داخل حاوية worker ← `INVALID_INPUT` بلا مخرجات جزئية ← إعادة تشغيل
worker والتقاط مهمة لاحقة ←
فحص تسريب التوكن/المسارات في الجسم الخام ← تأكيد عدم نشر منفذ 8000 على المضيف
← teardown كامل مع `trap`. المهمة في CI بلا `continue-on-error`: أي فشل يكسر
البوابة، ولا يُصنَّف Compose تشغيليًا إلا بنجاح رانر فعلي.

## 6. بنود غير متحققة صراحةً (لا اقتراح اعتماد قبل إغلاقها أو توثيقها خارج البوابة)

1. شهادة Let's Encrypt عامة حقيقية على مضيف نظيف مع DNS ومنافذ مفتوحة — الشهادة الداخلية لـlocalhost مُثبَتة فقط، والبند يتطلب بيئة مستهدفة.
2. قياسا 30 دقيقة وساعتين على VPS المستهدف بنفس السكربت؛ قياس الساندبوكس (القسم 4) فشل في تحقيق السقفين ويُعرض كما هو، ولا يغلق الهدف.
3. تدقيق تسريب أسرار شامل لكل المكونات (المغطى آليًا حاليًا: مسار فشل العامل + فحص التوكن في سجلات الحاويات ضمن compose-smoke).
4. تقرير القبول السابق منسوخ داخل المستودع في
   `D2_MVP/reports/AetherFlow_Task016_G2_FinalAcceptance_Report.md`؛ وهذا
   السجل هو المرجع الحيّ ويتفوق عليه عند التعارض.
