## 1. كيفية وصول ملف الرفع إلى العامل (تزويد العامل بالملف)

عقد الفصل ثابت ومُختبَر، ولا توجد نقطة تنزيل عامة:

```
عميل الـAPI                الطابور (SQLite)                العامل (الحاويتان تتشاركان /app/data)
     │                          │                                     │
     │  POST /jobs {file: "<id>"}                                       │
     │  (id opaque فقط، بلا مسارات)  validate_upload_id                 │
     │ ────────────────────────► │  يخزَّن: upload://<id>               │
     │                            │ ──────────────────────────────────► │ LocalUploadStore.resolve(id)
     │                            │                                     │  - إعادة تحقق من رمز الـid
     │                            │                                     │  - ربط داخل AETHERFLOW_UPLOAD_STORE
     │                            │                                     │  - حل الروابط الرمزية وفحص الاحتواء
     │                            │                                     │  - ملف عادي موجود داخل الجذر الموثوق
     │                            │                                     │  ▼
     │                            │                                     │ منفّذ FFmpeg ثم مخرجات نسبية
```

- الـAPI لا يقبل مسارات خادم إطلاقًا؛ `POST /uploads` **خارج نطاق D2** (D3).
- التزويد الفعلي للكائن داخل `AETHERFLOW_UPLOAD_STORE` يتم بقناة تشغيلية خارج
  الـAPI (إيداع مُوثَّق من مُشغّل/مكوّن استيعاب لاحق باسم الرمز المتحقَّق منه)؛
  في Compose الجذر داخل المجلد المتشارك `/app/data/upload_store` فتصل إليه
  حاويتا orchestrator وworker عبر نفس وحدة التخزين.
- فشل الحل يُغلق بمهمة `failed/INVALID_INPUT` بلا مسارات في الرسالة.

## 2. مصفوفة المعايير الوظيفية

| المعيار (`05_ACCEPTANCE_CRITERIA.md`) | الحالة | الدليل الفعلي |
|---|---|---|
| `POST /jobs` ينشئ مهمة ويعيد `id` بحالة `queued` | مُثبَت | `tests/api/test_jobs_api.py`؛ تشغيل حي بعمليتين: HTTP 202 و`queued` عبر curl حقيقي |
| `GET /jobs/{id}` يعرض الحالة والمخرجات | مُثبَت | نفس التشغيل الحي: `completed` بمرجع نسبي، `failed` بكود آمن |
| `GET /jobs` ترتيب `priority DESC, created_at ASC` وفلترة آمنة | مُثبَت | اختبارات الطابور والـAPI؛ حي: فلترتا `failed=1` و`completed=2` بالعد الصحيح |
| split على عينة قصيرة ينتج مقاطع قابلة للفك | مُثبَت | `tests/integration/` بثنائي حقيقي؛ فك مستقل `ffmpeg -v error -xerror -f null` رمز 0 بلا أخطاء؛ العدد يخضع لسلوك keyframes |
| `/health` يفشل بوضوح عند انقطاع DB بلا أسرار | مُثبَت | فحص `SELECT 1`؛ 200 حي، و503 عام بمحاكاة `_FailingQueue` (محاكاة `OperationalError`، لا فشل محرك حقيقي) بلا نص محرك/مسار/SQL |
| مسار غير موجود/خارج المجلد المسموح: رفض واضح | مُثبَت | ثلاث طبقات (طابور/مخزن رفع/منفّذ)؛ حي: `../etc/passwd` ← 400 |
| ملف أكبر من حد الإعداد: رفض قبل المعالجة | مُثبَت | اختبارات `EnqueuePolicy` والمنفّذ (الحد 2000MB من YAML) |
| مهمتان متزامنتان: التزام بحد التزامن | مُثبَت | `max_active` المقيس = الحد؛ ميزانية مشتركة بميزانيات 1/3/5 وتزامن 2 و3 بلا تجاوز |
| فشل FFmpeg: `failed` مع `error_type` آمن | مُثبَت | E2E لملف تالف وكائن مفقود؛ حي: `INVALID_INPUT` بلا مسار ولا مخرجات جزئية |
| إعادة التشغيل لا تفقد الطابور الدائم | مُثبَت | اختبار restart؛ حي: عملية عامل جديدة التقطت مهمة أُنشئت قبل تشغيلها على نفس ملف SQLite |

| Caddy/Let's Encrypt | غير مُثبَت تشغيليًا | `Caddyfile` وcompose معدّان؛ شهادة حقيقية تحتاج DNS ومنافذ عامة على مضيف نظيف، ولا يحاكيها الرانر المحلي |

### ماذا يغطي `scripts/verify_compose_stack.sh` (10 أقسام)

`docker compose config` ← عينة سليمة وتالفة في مجلد بيانات معزول ← بناء
وتشغيل المكدس ← فحوص health عبر شبكة Compose الداخلية ← queued→completed عبر
HTTP حقيقي من حاوية Caddy ← فك ترميز مستقل داخل حاوية worker ←
`INVALID_INPUT` بلا مخرجات جزئية ← إعادة تشغيل worker والتقاط مهمة لاحقة ←
فحص تسريب التوكن/المسارات في الجسم الخام ← تأكيد عدم نشر منفذ 8000 على المضيف
← teardown كامل مع `trap`. المهمة في CI بلا `continue-on-error`: أي فشل يكسر
البوابة، ولا يُصنَّف Compose تشغيليًا إلا بنجاح رانر فعلي.

## 4. مصفوفة الأداء للفيديو الطويل (قياسات فعلية)

العيّنتان مبنيّتان بدمج العينة الثابتة 5 ثوانٍ بلا إعادة ترميز
(`scripts/benchmark_long_media.sh`)، فالقياس لزمن التنفيذ لا لإعداد العينة.
زمن الجدار يقاس على **مسار المنفّذ الكامل شامل فحص الفك الإلزامي**؛ ويُسجَّل

مواصفات بيئة القياس (ليست VPS المستهدف): Linux x86_64، نواتا Intel Xeon
@2.60GHz، ذاكرة 4,034,452 KiB، FFmpeg 7.0.2-static، التاريخ 2026-10-25.

## 6. بنود غير متحققة صراحةً (لا اقتراح اعتماد قبل إغلاقها أو توثيقها خارج البوابة)

1. نجاح `compose-smoke` على رانر CI الفعلي (البناء/التشغيل/إعادة التشغيل/الصحة/الأمان) — أول تشغيل فشل بصلاحيات الـbind mount والإصلاح مرفوع؛ البند مفتوح حتى نجاح الرانر.
2. شهادة Let's Encrypt حقيقية على مضيف نظيف مع DNS — تتطلب بيئة مستهدفة.
3. قياسا 30 دقيقة وساعتين على VPS المستهدف بنفس السكربت؛ قياس الساندبوكس فشل في تحقيق السقفين ويُعرض كما هو.
4. تدقيق تسريب أسرار شامل لكل المكونات (المغطى آليًا حاليًا: مسار فشل العامل).
5. تقرير القبول السابق منسوخ داخل المستودع في
   `D2_MVP/reports/AetherFlow_Task016_G2_FinalAcceptance_Report.md`؛ هذا
   السجل هو المرجع الحيّ ويتفوق عليه عند التعارض.
