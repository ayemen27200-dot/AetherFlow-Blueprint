# خطة التحقق التشغيلي على VPS — AetherFlow D2/G2

> خطة خطوة-بخطوة لوكيل تحقق مستقل يملك وصولًا مصرّحًا به إلى الخادم. وكيل
> الإعداد لم ينفّذ أيًّا منها على VPS. كل خطوة تعرض سبعة حقول: الهدف،
> المتطلبات السابقة، الإجراء، النتيجة المتوقعة، الدليل المطلوب، شروط
> النجاح/الفشل، والتوقف الآمن.
>
> اصطلاحات ثابتة:
> - أنشئ مجلد الأدلة أولًا وصدّر مساره:
>   `EVIDENCE_DIR="$HOME/aetherflow-vps-evidence/$(date -u +%Y%m%dT%H%M%SZ)"; mkdir -p "$EVIDENCE_DIR"`
> - كل أمر يُحفَظ بنمط `run_ev` المعرّف في `COMMANDS_AND_EVIDENCE.md` (أمر،
>   توقيت UTC، رمز خروج، مخرجات كاملة).
> - المستوى (قراءة فقط / معزول / بموافقة) موسوم لكل خطوة. لا تتجاوز مستوى
>   التفويض الذي منحه مالك الخادم.
> - لا تُدخِل أي سر في سطر الأوامر إن أمكن كشفه في سجل shell؛ استخدم المتغيرات
>   والملفات ذات الوضع 0600، ولا تطبع قيمها أبدًا.

---

## خطوة 0 — بوابة التفويض والمعلومات (إدارية، بلا أوامر على الخادم)

- **الهدف:** التأكد أن التحقق سيجري على المضيف الصحيح وبصلاحية قانونية، وأن
  المعلومات المجهولة لدى وكيل الإعداد متوفرة.
- **المتطلبات السابقة:** تكليف رسمي من مالك الخادم.
- **الإجراء:** اجمع إجابات القسم 8 من `README_HANDOFF.md`: التوزيعة/الإصدار/
  المعمارية، المستخدم و`sudo`، هل المضيف إنتاجي أم اختباري، الموارد القائمة
  التي لا تُلمس، حالة Docker/Python، النطاق وDNS والمنافذ، مواصفات العتاد،
  الملفات الممثلة وترخيصها، وقناة تزويد `BEARER_TOKEN`.
- **النتيجة المتوقعة:** ورقة تفويض مكتوبة تحدد المضيف ونطاق الفحوص المسموح بها.
- **الدليل المطلوب:** نسخة من التفويض (بعد إخفاء أي بيانات حساسة) في مجلد
  الأدلة.
- **النجاح:** كل المعلومات الحرجة حاضرة وموقّعة من المالك.
- **الفشل:** أي نقطة جوهرية ناقصة (مثلًا: مضيف إنتاجي بلا تحديد نافذة عمل، أو
  ملفات قياس بلا ترخيص) — لا تبدأ الفحص.
- **التوقف الآمن:** توقف واطلب المعلومة الناقصة؛ لا تخمّن بنية أو مسارًا.

## خطوة 1 — هوية الخادم وإصدارات النظام (قراءة فقط)

- **الهدف:** إثبات هوية البيئة الفعلية ومتطلبات التشغيل قبل أي تغيير.
- **المتطلبات السابقة:** بوابة التفويض مكتملة.
- **الإجراء:**
  ```bash
  run_ev 01-identity bash -c '
    date -u +%FT%TZ; hostname; id; uname -a;
    cat /etc/os-release; dpkg --print-architecture 2>/dev/null || true;
    nproc; grep -m1 "model name" /proc/cpuinfo;
    awk "/MemTotal/ {print}" /proc/meminfo; df -P "$HOME";
    command -v docker && docker --version || echo "docker: absent";
    docker compose version 2>/dev/null || echo "compose v2: absent";
    command -v python3 && python3 --version;
    command -v ffmpeg && ffmpeg -version | head -1 || echo "ffmpeg: absent";
    command -v ffprobe && ffprobe -version | head -1 || echo "ffprobe: absent";
    command -v git && git --version'
  ```
- **النتيجة المتوقعة:** سجل كامل بالهوية والإصدارات والعتاد. المُثبّت
  `scripts/install_vps.sh` يدعم Ubuntu فقط (يفحص `ID=ubuntu` واسم الكود
  بنفسه ويتوقف بغيرها).
- **الدليل المطلوب:** `01-identity.log`.
- **النجاح:** البيانات التقطت كما هي بلا تعديل، ومتطلبات التشغيل معروفة
  (الحاضر/الغائب).
- **الفشل:** غياب أداة جوهرية لا يُعد فشل كود — سجله كفجوة متطلبات وانتقل
  للخيارات المعزولة التي لا تحتاجها، أو اطلب تثبيتًا بموافقة (طبقة 3).
- **التوقف الآمن:** هذه الخطوة لا تغير شيئًا؛ أي خطأ صلاحيات يُسجَّل ويُتجاوز
  إلى الأوامر المسموح بها دون `sudo`.

## خطوة 2 — المستودع والفرع ومطابقة الـSHA (قراءة فقط)

- **الهدف:** إثبات أن الكود المختبر هو نسخة الفرع المقصود بحالة شجرة نظيفة.
- **المتطلبات السابقة:** حق وصول للقراءة إلى GitHub (أو نسخة مستودع زوّدك بها
  المالك عبر قناته الآمنة).
- **الإجراء:**
  ```bash
  # إن لم يوجد استنساخ:
  git clone https://github.com/ayemen27200-dot/AetherFlow-Blueprint.git
  cd AetherFlow-Blueprint
  git checkout arena/940efcbe-aetherflow-blueprint
  # وإن وجد:
  git fetch origin arena/940efcbe-aetherflow-blueprint
  git status --porcelain
  git rev-parse HEAD
  git remote -v
  git log --oneline -5
  ```
- **النتيجة المتوقعة:** شجرة عمل نظيفة (`git status --porcelain` بلا مخرجات)،
  والفرع هو `arena/940efcbe-aetherflow-blueprint`. الرأس الأساسي للحقيبة هو
  `448526a4a52f45b0c5f7a667f5c27e3493595534`، لكن الرأس الفعلي قد يكون أحدث
  (دفعات أدلة لاحقة)؛ الأهم تسجيل الـSHA الفعلي وربطه بتشغيله الأخضر.
- **الدليل المطلوب:** نواتج الأوامر كاملة في `02-git-state.log`، والـSHA
  الفعلي في `RESULTS_TEMPLATE.md`.
- **النجاح:** SHA مسجَّل ومطابق لالتزام على الفرع، ويمكن ربطه بتشغيل CI عبر
  `gh run list --branch arena/940efcbe-aetherflow-blueprint --limit 5`.
- **الفشل:** شجرة متسخة أو فرع مختلف أو تعذّر الوصول — لا تختبر كودًا مجهول
  المصدر؛ أبلغ المالك وانتظر التوجيه.
- **التوقف الآمن:** لا تستخدم `git reset --hard` ولا أي تنظيف يمحو تعديلات
  محلية قد تخص المالك؛ توقف واستفسر.

## خطوة 3 — مراجعة الإعدادات والأسرار دون طباعتها (قراءة فقط)

- **الهدف:** التأكد من بنية الأسرار السليمة (وجود، أوضاع، تجاهل Git) دون كشف
  أي قيمة.
- **المتطلبات السابقة:** الخطوة 2.
- **الإجراء:**
  ```bash
  run_ev 03-secrets bash -c '
    echo "--- .env presence/mode (no content printed) ---";
    if [ -e .env ]; then stat -c "%a %U %G %n" .env; else echo ".env absent"; fi;
    echo "--- ignore rule ---";
    git check-ignore -v .env || echo "WARN: .env not ignored";
    echo "--- tracked secret templates must hold blank values only ---";
    git ls-files | grep -E "(^|/)\.env" ;
    grep -nE "^[A-Z0-9_]+=.+" .env.example || echo ".env.example: only blank assignments";
    echo "--- private keys tracked? (expect none) ---";
    git ls-files | grep -E "\.(pem|key|p12)$" || echo "no key files tracked";
    echo "--- media/db tracked? (expect only the 5s fixture) ---";
    git ls-files | grep -E "\.(mp4|mkv|mov|wav|mp3|db)$" || true'
  ```
- **النتيجة المتوقعة:** `.env` (إن وُجد) وضع 0600 ومتجاهَل في Git؛ النموذج
  المتعقَّب `.env.example` بلا قيم سرية؛ لا مفاتيح خاصة ولا ملفات وسائط/قواعد
  بيانات متعقَّبة عدا `tests/fixtures/sample_5s.mp4`.
- **الدليل المطلوب:** `03-secrets.log` (لا يحتوي أصلًا أي قيمة سرية).
- **النجاح:** كل بند أعلاه في موضعه السليم.
- **الفشل:** ظهور ملف سر/مفتاح متعقَّب أو نموذج يحمل قيمة فعلية — سجله كنتيجة
  فعلية ولا تحذف شيئًا بنفسك.
- **التوقف الآمن:** ممنوع منعًا باتًا `cat .env` أو طباعة التوكنات أو تعديل
  أذونات ملفات المالك؛ أي إصلاح يتطلب موافقته.

## خطوة 4 — فحص Compose وCaddy والمنافذ دون تشغيل (قراءة فقط)

- **الهدف:** التحقق البنيوي من المكدس المعلَن: خدماته، عدم نشر منفذ التطبيق،
  Caddy كمدخل عام وحيد، وأوضاع التصليب.
- **المتطلبات السابقة:** الخطوة 2؛ Docker وCompose v2 للفحص المُصيَّر (وإلا
  فالمراجعة اليدوية للملفات مقبولة وتُعلَّم).
- **الإجراء:**
  ```bash
  run_ev 04-compose-config docker compose -f docker/docker-compose.yml config
  # منافذ الاستماع على المضيف (قراءة، بلا sudo قدر الإمكان):
  ss -tln | tee "$EVIDENCE_DIR/04-listening-sockets.log"
  # موارد Compose القائمة على المضيف وعدم لمسها:
  docker ps -a --filter "label=com.docker.compose.project=aetherflow" \
    --format '{{.Names}} {{.Status}} {{.Ports}}' | tee "$EVIDENCE_DIR/04-existing-project.log"
  ```
- **النتيجة المتوقعة:** الإعداد المُصيَّر يُظهر الخدمات الثلاث `orchestrator`
  و`worker` و`caddy`؛ لا يحتوي orchestrator على `published` للمنفذ 8000
  (استخدام `expose` فقط داخل الشبكة)؛ Caddy وحده ينشر 80/443؛ الحاويات بلا
  صلاحيات جديدة (`no-new-privileges`) و`cap_drop: ALL` ومستخدم غير جذري
  uid 1000 وفق `docker/Dockerfile.orchestrator`.
- **الدليل المطلوب:** `04-compose-config.log` وملفي اللقطات.
- **النجاح:** البنية تطابق `docker/docker-compose.yml` و`docker/Caddyfile`،
  ولا مشروع قائم سيُلمس (السكربت المعزول لا يستخدم الاسم الثابت `aetherflow`).
- **الفشل:** ظهور منفذ 8000 منشورًا للمضيف، أو خدمة غير معلنة — سجله كخلل
  بنيوي ولا تبدأ تشغيلًا إنتاجيًا.
- **التوقف الآمن:** لا تعدّل ملفات Compose ولا الجدار الناري ولا توقف خدمات
  قائمة؛ الفحص قراءة فقط.

## خطوة 5 — بيئة Python معزولة والفحوص المحلية الكاملة (معزول)

- **الهدف:** إعادة إنتاج وظيفة `verify` في CI على الخادم نفسه، بأدلة JUnit
  محلية.
- **المتطلبات السابقة:** Python 3.11+؛ تثبيت FFmpeg/FFprobe على المضيف أو
  إذن بتثبيتهما؛ الكتابة داخل مجلد المستودع فقط (venv ومجلد `data/` المتجاهَل).
- **الإجراء:**
  ```bash
  run_ev 05a-venv bash -c 'python3 -m venv .venv && .venv/bin/pip install --upgrade pip && .venv/bin/pip install -e ".[dev]"'
  run_ev 05b-bash-syntax bash -c 'for s in scripts/*.sh; do bash -n "$s" || exit 1; done'
  run_ev 05c-specs .venv/bin/python scripts/validate_specs.py
  run_ev 05d-openapi .venv/bin/openapi-spec-validator D1_FOUNDATION/03_API_SPEC.yaml
  run_ev 05e-compileall .venv/bin/python -m compileall -q agent orchestrator executors web scripts
  run_ev 05f-ruff .venv/bin/ruff check .
  mkdir -p data/vps-evidence
  run_ev 05g-pytest env AETHERFLOW_REQUIRE_MEDIA_BINARIES=1 \
    .venv/bin/python -m pytest -q -ra --junitxml=data/vps-evidence/junit.xml
  .venv/bin/python scripts/summarize_junit.py data/vps-evidence/junit.xml | tee "$EVIDENCE_DIR/05h-junit-summary.txt"
  cp data/vps-evidence/junit.xml "$EVIDENCE_DIR/"
  ```
- **النتيجة المتوقعة:** كل الأوامر رمز خروجها 0؛ مع وجود الثنائيات والحارس
  `AETHERFLOW_REQUIRE_MEDIA_BINARIES=1` لا يُتخطى اختبار وسائط المعالجة،
  فتُنفَّذ المجموعة كاملة على الخادم. في بيئة الإعداد الحالية تُجمَع 210 حالة
  (208 ناجحة ومتخطّيان بيئيان)؛ هذا رقم بيئة الإعداد لا رقم رانر، والعدد
  المرجعي لرأسك الفعلي خذه حصريًا من `junit.xml` الذي تنتجه محاولتك، ولا
  تنقل عددًا من هذه الوثيقة.
- **الدليل المطلوب:** كل السجلات + `junit.xml` + الملخص.
- **النجاح:** 0 فشل و0 خطأ؛ أي تخطٍّ يُسجَّل بسببه الصريح (مثل غياب ffprobe).
- **الفشل:** أي فشل اختبار يوقف ادعاء التحقق للبند المقابل؛ احفظ المخرجات
  الخام كما هي بلا انتقاء.
- **اختبار توقيت معروف حسّاس للجدولة (سجّله بأمانة إن صادفته):**
  `tests/integration/test_split_e2e.py::test_timeout_terminates_real_subprocess`
  (السطر 244 تقريبًا) يضبط مهلة 1ms بينما حلقة مراقبة العملية تتفقد كل 100ms
  (راجع `_run_subprocess` في `executors/ffmpeg.py`)، فيمكن في الجدولات
  السريعة أن تكتمل العملية الفرعية الصغيرة أول دورة قبل ملاحظة تجاوز المهلة،
  فيُرفَض الاختبار بـ`DID NOT RAISE ExecutorTimeoutError`. على ساندبوكس البناء
  المشترك نواتين رُصد تكرار ~2 من 15 إعادة معزولة؛ وتشغيلات CI المسجّلة على
  الرانر لم ترصد الفشل. هذا تقلقل بيئي محتمل في اختبار سباقي وليس خللًا في
  منطق المهلة الإنتاجية (المهلة الافتراضية للوظائف 3600ث ولفحوص الفك 60ث). إن
  صادفته: أعد تشغيل الاختبار المعزول 10 مرات وسجّل معدل التكرار الفعلي على
  خادمك، ولا تخفِه، ولا تعدّل الكود ضمن جلسة التحقق — أي إصلاح قرار مراجعة
  منفصل.
- **التوقف الآمن:** كل الأثر داخل `.venv/` و`data/` (متجاهَلان في Git)؛ لا
  تثبّت حزمًا على نظام الخادم خارج الـvenv دون موافقة.

## خطوة 6 — تحقق مكدس Docker المعزول وغير المدمر (معزول)

- **الهدف:** إثبات المسار التشغيلي الكامل على Docker الخاص بالخادم المستهدف
  عبر السكربت المعزول القائم في المشروع.
- **المتطلبات السابقة:** Docker Engine + Compose v2 وصلاحية استخدام العفريت
  (مجموعة `docker` أو `sudo docker` بموافقة)؛ مساحة قرص لبناء صورة؛ الخطوة 4.
- **الإجراء:**
  ```bash
  run_ev 06-isolated-compose bash scripts/verify_compose_stack.sh
  ```
- **ماذا يفعل السكربت فعلًا (راجع المصدر قبل التشغيل):** مجلد عمل فريد عبر
  `mktemp` تحت `/tmp`، مشروع Compose فريد `aetherflowsmoke<ts>-<pid>`، وسم
  صورة فريد ووحدة تخزين مسماة فريدة، وملف env مؤقت وضع 0600 بتوكن عابر؛ يبني
  الصورة ويشغّل ثلاث حاويات ثم ينفّذ 11 قسمًا: (1) العزل والبذر، (2) فحص
  `compose config` ومنع نشر 8000، (3) بناء وتشغيل، (4) صحة DB حية عبر
  `/health` داخل الشبكة، (5) مهمة سعيدة queued→completed عبر HTTP حقيقي،
  (6) فك ترميز مستقل لمخرجات حقيقية داخل حاوية العامل، (7) مدخل تالف →
  `failed/INVALID_INPUT` بلا مخرجات جزئية، (8) استمرارية الطابور بعد إعادة
  تشغيل العامل، (9) فحص تسرب التوكن والمسارات و401 بدون توكن ورفض معرّف
  شبيه بمسار (400)، (10) تأكيد عدم نشر منفذ 8000، (11) إثبات عدم التدخل مع
  مشروع `aetherflow` الثابت وشجرة `data/` بالمستودع. عند أي فشل يطبع
  تشخيصًا ثم يزيل مشروعه الفريد وحده عبر `trap` (لا يلمس أي مورد آخر).
- **النتيجة المتوقعة:** السطر الأخير
  `PASS: isolated compose stack verification finished successfully`.
- **الدليل المطلوب:** السجل الكامل `06-isolated-compose.log` (السكربت يطبع
  أيضًا مسارات سجل البناء داخل مجلده المؤقت قبل إزالته؛ التقط كل المخرجات).
- **النجاح:** PASS ورمز خروج 0، مع تطابق أقسام السكربت الـ11 مع ما رصدته.
- **الفشل:** أي قسم FAIL يوقف التشغيل تلقائيًا مع تشخيص؛ سجله كما هو ولا
  تعالج السبب بتعديلات على النظام دون موافقة.
- **التوقف الآمن:** السكربت مصمم ليكون غير مدمر (راجع `tests/unit/test_verifier_isolation.py`
  الذي يثبت القيود)؛ لا تشغّل نسخة معدّلة منه، ولا تضيف أعلامًا تحذف مجلدات
  أخرى. إن رفض السكربت البدء بسبب اسم مشروع قائم، توقف وأبلغ المالك.

## خطوة 7 — (اختياري) مسار العمليتين المحلي بفحوص يدوية (معزول)

- **الهدف:** تأكيد تشغيلي حي إضافي خارج Docker: عملية API منفصلة وعملية عامل
  منفصلة تتشاركان ملف SQLite، بفحوص التالف والرفض والاستمرارية يدويًا.
- **المتطلبات السابقة:** الخطوة 5؛ كل الأثر تحت `data/local-e2e-<ts>/`
  المتجاهَل؛ الربط على 127.0.0.1 فقط.
- **الإجراء (ملخص؛ التفاصيل في `COMMANDS_AND_EVIDENCE.md` القسم 2.3):**
  1. ولّد توكنًا في متغير بيئة (لا تكتبه في ملف متعقَّب)، شغّل
     `uvicorn orchestrator.main:app --host 127.0.0.1 --port 8000` ثم
     `aetherflow worker run` بمسارات معزولة.
  2. انسخ `tests/fixtures/sample_5s.mp4` إلى مخزن الرفع باسم
     `up-sample-5s.mp4` وأنشئ نسخة تالفة عمدًا.
  3. اختبر: 401 بدون توكن، 400 لمعرّف شبيه بمسار، 202 ثم `completed` لمهمة
     سليمة، فك مستقل للمخرجات بـ`ffmpeg -v error -xerror -f null`، ثم
     `failed/INVALID_INPUT` للتالف وغياب أي مجلد مخرجات جزئي.
  4. للاستمرارية: أوقف العامل، أنشئ مهمة جديدة (تبقى `queued`)، شغّل عاملًا
     جديدًا على نفس ملف SQLite وأكّد التقاطها وإكمالها.
- **النتيجة المتوقعة:** نفس سلوك أقسام السكربت المعزول ولكن عبر عمليات
  منفصلة يدويا.
- **الدليل المطلوب:** سجل جلسة كامل مع رموز الخروج، ولقطات JSON للوظائف.
- **النجاح:** كل الحالات أعلاه مطابقة والعنوان ملزم 127.0.0.1.
- **الفشل:** أي انحراف يُسجَّل بعبارة الفعل الفعلية ورمز HTTP.
- **التوقف الآمن:** أوقف العمليتين بـSIGTERM بعد الانتهاء؛ لا تترك منفذًا
  مفتوحًا على واجهة عامة، ولا تستخدم منفذًا مستخدمًا أصلًا على الخادم.

- **المتطلبات السابقة:** الخطوة 6 (مكدس معزول) أو إذن على مكدس قائم.

- **النتيجة المتوقعة:** سجلات منظمة بلا توكنات أو مسارات مطلقة (راجع خطوة 11).
- **الدليل المطلوب:** الملفات الثلاثة بعد الإخفاء.

- **الفشل:** تعذّر الوصول إلى مورد أو ظهور سر في السجلات — يُسجَّل كنتيجة فعلية

## خطوة 9 — قياس الأداء ببروتوكول المشروع (معزول، 3 إعادات لكل مدة)

- **الهدف:** الحكم على معياري 15ث (30 دقيقة) و60ث (ساعتان) بقياس VPS فعلي.
- **المتطلبات السابقة:** الخطوة 5 (venv وفيه أمر `aetherflow`)، ثنائيا
  ffmpeg/ffprobe، ملفان ممثلان حقيقيان مرخّصان (المساران في
  `BENCH_30M_INPUT` و`BENCH_2H_INPUT`)؛ أو الوضع الاصطناعي مع تعليم المخرجات
  صراحةً أنها اصطناعية غير ممثلة. لا موارد مدفوعة ولا عتاد إضافي دون موافقة.
- **الإجراء (دون أي تعديل على السكربت أو المعايير):**
  ```bash
  BENCH_REPEATS=3 \
  BENCH_30M_INPUT=/path/authorized/30m.mp4 \
  BENCH_2H_INPUT=/path/authorized/2h.mp4 \
  FFMPEG="$(command -v ffmpeg)" FFPROBE="$(command -v ffprobe)" \
    bash scripts/benchmark_long_media.sh 2>&1 | tee "$EVIDENCE_DIR/09-benchmark.log"
  cp data/bench/RESULTS.md "$EVIDENCE_DIR/09-RESULTS.md"
  ```
- **حقول البروتوكول الثابتة (من المصدر):** السكربت يقيس زمن الجدار لمسار
  المنفّذ الكامل شامل فك الفك الإلزامي للمدخل ولكل جزء (خروج 0 وتيار أخطاء
  فارغ و`-xerror`)؛ يسجّل مواصفات الجهاز وإصدارات الأدوات ورأس Git وحالة
  الاتساخ وعدد الإعادات وخصائص الوسائط، ويكتب جدولًا بكل محاولة ثم الوسيط
  والأصغر والحكم (`PASS` فقط إن كان الوسيط دون السقف، وإلا `OPEN`). يحذف
  مجلده المخصص `data/bench` وحده (حارس مسار في الكود) قبل البدء.
- **النتيجة المتوقعة:** `data/bench/RESULTS.md` بثلاث قيم جدارية لكل مدة
  ووسيط محسوب، وكل المخرجات مجتازة فحص السلامة (مدمج في المنفّذ).
- **الدليل المطلوب:** السجل الكامل، `data/bench/RESULTS.md`، مواصفات العتاد من خطوة 1،
  وترخيص/مصدر الملفين.
- **النجاح:** الوسيط < السقف في كل المدّتين مع سلامة المخرجات — وعندها فقط
  يقفل البند، بقرار المراجع.
- **الفشل/التجاوز:** أي قيمة فوق السقف تُسجَّل كما هي (الحكم `OPEN`)؛ لا
  تخفِ محاولة، ولا تغيّر السقف، ولا تعطّل فك الفك. إن تعذّرت الملفات الممثلة،
  اكتفِ بالوضع الاصطناعي وعلّم النتيجة «اصطناعية، لا تغلق المعيار».
- **تحذير تشغيلي موثّق:** لا ترفع `AETHERFLOW_VERIFY_CONCURRENCY` فوق عدد
  الأنوية؛ على نواتين سبّبت القيمة 3 تجاوز مهلة الفك 60ث ورفض مدخل سليم
  بتصنيف `INVALID_INPUT` (تقرير Task020). اترك الافتراضي `min(8, الأنوية)`.
- **التوقف الآمن:** السكربت معزول في `data/`؛ انسخ النتائج فورًا لأن إعادة
  التشغيل تعيد إنشاء المجلد. لا تلمس أي بيانات إنتاجية.

## خطوة 10 — شهادة TLS العامة (شرطية — فقط مع DNS ومنافذ حقيقية)

- **الهدف:** التحقق من شهادة Let's Encrypt عامة على اسم نطاق فعلي، وعدم
  الخلط بينها وبين شهادة Caddy الداخلية.
- **المتطلبات السابقة:** اسم نطاق حقيقي سجله يشير إلى الخادم، ومنفذا 80/443
  متاحان، وموافقة المالك على أي تشغيل يخص الشبكة العامة. غياب هذه الشروط
  يعني وضع علامة «غير متحقق» وليس فشل الكود.
- **الإجراء (قراءة فقط من الخادم/أي عميل):**
  ```bash
  getent hosts "$DOMAIN"
  curl -sS -o /dev/null -w 'http=%{http_code} ssl_verify=%{ssl_verify_result}\n' "https://$DOMAIN/health"
  echo | openssl s_client -connect "$DOMAIN:443" -servername "$DOMAIN" 2>/dev/null \
    | openssl x509 -noout -subject -issuer -dates
  ```
- **النتيجة المتوقعة للنجاح:** `ssl_verify=0`، المُصدِر جهة عامة موثوقة في
  سلسلة Let's Encrypt (وليس `Caddy Local Authority`)، التواريخ سارية،
  والموضوع يطابق اسم النطاق، و`/health` يستجيب 200 عبر الوكيل.
- **الدليل المطلوب:** المخرجات الكاملة ونسخة الشهادة (بلا مفاتيح خاصة):
  `openssl s_client ... | openssl x509 -outform PEM > "$EVIDENCE_DIR/10-cert.pem"`.
- **النجاح:** شهادة عامة موثوقة على النطاق الفعلي.
- **الفشل/عدم الانطباق:** شهادة داخلية (`issuer` يحوي Caddy Local Authority)
  أو خطأ سلسلة الثقة أو غياب DNS → النتيجة «غير متحقق» مع السبب الصريح.
- **التوقف الآمن:** لا تفتح منافذ ولا تعدّل سجلات DNS ولا `DOMAIN`/`ACME_EMAIL`
  ولا تعيد تشغيل Caddy في بيئة إنتاجية دون موافقة؛ كلها طبقة 3.

## خطوة 11 — تدقيق تسرب الأسرار الشامل (قراءة فقط + تحليل)

- **الهدف:** تغطية أوسع من الفحص الآلي القائم (مسار فشل العامل وفحص توكن
  سجلات الحاويات) لتشمل المحتوى المتعقَّب والسجلات والمخرجات والأوضاع.
- **المتطلبات السابقة:** الخطوات 3، 6، 8.
- **الإجراء:**
  ```bash
  # أ) أنماط أسرار في المحتوى المتعقَّب (قراءة فقط):
  git grep -nI -E 'BEGIN ([A-Z ]+ )?PRIVATE KEY|api[_-]?key|secret|token|password' -- . \
    | tee "$EVIDENCE_DIR/11a-tracked-patterns.log"   # تُراجَع يدويًا: المتوقع أسماء متغيرات ونماذج فارغة فقط
  # ب) فحص توكن حي في سجلات الحاويات (القيمة في متغير لا تُطبع):
  #    لمكدس قائم بموافقة، أو أرشف سجل الخطوة 6 المعزول:
  if [ -n "${BEARER_TOKEN:-}" ]; then
    docker compose -f docker/docker-compose.yml logs --no-color 2>/dev/null \
      | grep -F "$BEARER_TOKEN" && echo "LEAK FOUND" || echo "no token in logs"
  fi
  # ج) مسارات مطلقة في متن استجابات الوظائف (عيّنة من سجلات الخطوة 6/7):
  grep -E '/app/|/home/|/var/' "$EVIDENCE_DIR"/0[67]*.log || echo "no absolute paths in evidence"
  # د) أوضاع المجلدات الحساسة إن وُجد مكدس بيانات:
  stat -c '%a %U %G %n' data data/upload_store data/outputs 2>/dev/null || true
  ```
- **النتيجة المتوقعة:** لا أسرار فعلية في المحتوى المتعقَّب، لا توكن في
  السجلات، لا مسارات مطلقة في استجابات API، أوضاع `data/` 0750 بملكية uid
  1000 حيث ينطبق تصميم المُثبّت.
- **الدليل المطلوب:** ملفات الفحص الأربعة بعد إخفاء أي قيمة حساسة وفق
  `COMMANDS_AND_EVIDENCE.md` القسم 5.
- **النجاح:** كل الفحوص نظيفة أو بنتائج قابلة للتفسير كأسماء متغيرات فقط.
- **الفشل:** أي سر حقيقي مكشوف يُسجَّل فورًا كناتج فعل (مكان، نوع، دون نسخ
  القيمة كاملة) ويُرفع للمالك؛ لا تحاول التطهير بنفسك.
- **التوقف الآمن:** لا حذف لسجلات ولا تعديل صلاحيات واسع؛ هذا تدقيق قراءة فقط.
